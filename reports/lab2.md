### 1.请列举 SV39 页表页表项的组成，描述其中的标志位有何作用?
SV39 页表项为 **64 位**，实际使用低 **54 位**，组成如下：

- **44-54 位**：保留给未来拓展（当前必须为 0）
- **28-43 位**：**PPN[2]**（物理页号最高 16 位）
- **19-27 位**：**PPN[1]**（物理页号中间 9 位）
- **10-18 位**：**PPN[0]**（物理页号最低 9 位）
- **8-9 位**：**RSW**（预留给内核软件使用，这里没用到）
- **7 位**：**D**（Dirty，页被写过）
- **6 位**：**A**（Accessed，页被访问过）
- **5 位**：**G**（Global，全局映射，不刷 TLB，没用到）
- **4 位**：**U**（User，用户态可访问）
- **3 位**：**X**（Execute，可执行）
- **2 位**：**W**（Write，可写）
- **1 位**：**R**（Read，可读）
- **0 位**：**V**（Valid，页表项有效）

**标志位作用**：
- **V**：页表项有效位，为 0 时访问产生缺页异常。
- **R/W/X**：控制读写执行权限。全 0 表示指向下一级页表，否则为叶子页表。
- **U**：U=1 时用户态可访问，U=0 仅内核态访问。
- **G**：全局页，上下文切换时不刷该 TLB 项。
- **A**：硬件在访问页时置 1，操作系统可借此实现访问计数或换出。
- **D**：硬件在写页时置 1，用于实现脏页跟踪。
- **RSW**：给操作系统自定义用途。

### 2.缺页
缺页指的是进程访问页面时页面不在页表中或在页表中无效的现象，此时 MMU 将会返回一个中断， 告知 os 进程内存访问出了问题。os 选择填补页表并重新执行异常指令或者杀死进程。

#### 请问哪些异常可能是缺页导致的？
- **指令页错误**（Instruction Page Fault）：取指令时缺页
- **数据页错误**（Load Page Fault）：读内存时缺页
- **存储页错误**（Store/AMO Page Fault）：写内存时缺页

#### 发生缺页时，描述相关重要寄存器的值，上次实验描述过的可以简略。

| 寄存器            | 作用                                   |
|----------------|--------------------------------------|
| `sepc`         | 触发缺页的指令地址，OS 处理完后需返回到此指令重新执行        |
| `scause`       | 异常原因编码，区分是读、写还是取指缺页                |
| `stval`        | 发生缺页的虚拟地址 |
| `sstatus`      | 中断使能位、特权级状态等                       |
| `satp`         | 当前进程的页表物理地址           |

OS 通过 `stval` 拿到缺页虚址，查页表分配物理页，填页表项，最后 `sret` 回到 `sepc` 重试指令。


缺页有两个常见的原因，其一是 Lazy 策略，也就是直到内存页面被访问才实际进行页表操作。 比如，一个程序被执行时，进程的代码段理论上需要从磁盘加载到内存。但是 os 并不会马上这样做， 而是会保存 .text 段在磁盘的位置信息，在这些代码第一次被执行时才完成从磁盘的加载操作。

#### 这样做有哪些好处？
- **节省内存**：不必为未使用的页面分配物理内存，减少内存浪费。
- **加快启动速度**：程序启动时不必等待所有页面加载完成，只需加载必要的页面即可，提升响应速度。
- **提高效率**：许多程序可能只使用部分功能，Lazy 策略避免了不必要的页面加载，提高整体效率。


其实，我们的 mmap 也可以采取 Lazy 策略，比如：一个用户进程先后申请了 10G 的内存空间， 然后用了其中 1M 就直接退出了。按照现在的做法，我们显然亏大了，进行了很多没有意义的页表操作。

#### 处理 10G 连续的内存页面，对应的 SV39 页表大致占用多少内存 (估算数量级即可)？
10G 内存需要的页数为 `10G / 4K = 2^34 / 2^12 = 2^22` 页。每个页表项占 8 字节，因此需要的页表内存为 `2^22 * 8B = 2^25 B = 32MB`。因此，处理 10G 连续内存页面的 SV39 页表大致占用 几十 MB 的内存。

#### 请简单思考如何才能实现 Lazy 策略，缺页时又如何处理？描述合理即可，不需要考虑实现。
实现 Lazy 策略可以在 mmap 时不立即分配物理页，而是记录虚拟地址范围。当访问该范围的虚拟地址时触发缺页异常，OS 通过 `stval` 获取缺页地址，查找记录的映射信息，分配物理页并从文件加载数据到该页，更新页表项后返回继续执行指令。

缺页的另一个常见原因是 swap 策略，也就是内存页面可能被换到磁盘上了，导致对应页面失效。

#### 此时页面失效如何表现在页表项(PTE)上？
当页面被换出到磁盘时，页表项的 Valid 位（V）会被清零，表示该页表项无效。此时访问该虚拟地址会触发缺页异常，OS 需要从磁盘加载页面回内存，更新页表项并设置 Valid 位后继续执行指令。

### 3. 双页表与单页表

为了防范侧信道攻击，我们的 os 使用了双页表。但是传统的设计一直是单页表的，也就是说， 用户线程和对应的内核线程共用同一张页表，只不过内核对应的地址只允许在内核态访问。 (备注：这里的单/双的说法仅为自创的通俗说法，并无这个名词概念，详情见 KPTI )

#### 在单页表情况下，如何更换页表？
当发生系统调用或中断时，CPU 会自动切换到内核态，但页表保持不变，在切换进程时，才写入satp寄存器更换页表。
#### 单页表情况下，如何控制用户态无法访问内核页面？（tips:看看上一题最后一问）
PTE的U位为0，表示该页仅内核态可访问，用户态访问会触发缺页异常。
#### 单页表有何优势？（回答合理即可）
系统调用、中断处理无需切换页表，减少 TLB 冲刷开销，实现简单，页表维护成本低

#### 双页表实现下，何时需要更换页表？假设你写一个单页表操作系统，你会选择何时更换页表（回答合理即可）？
用户态与内核态切换时（如系统调用、中断、异常）必须切换页表，用户进程切换时也需要切换页表。

单页表操作系统可以选择在用户进程切换时更换页表，系统调用和中断处理时不切换页表。
